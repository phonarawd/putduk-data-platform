# v0.2.0 Auth / Edge Rollback Preflight

기준일: 2026-09-22 KST

이 문서는 v0.2.0 Production cutover 전에 Supabase Auth URL 설정과 Edge Function rollback 안전성을 확인하는 보조 SSOT다. GitHub Actions 성공 여부를 release 승인 근거로 사용하지 않는다.

## 1. 현재 상태

- Production Auth `site_url` / `uri_allow_list`: **UNCONFIRMED**
- final member origin: **UNRESOLVED**
- final ops origin: **UNRESOLVED**
- final Auth redirect allow-list: **UNRESOLVED**
- Production Auth config mutation: **0**
- Production Edge rollback execution: **0**

최종 도메인을 추측하지 않는다. 기존 `hiptk.app` / `putduk.kr` 값은 inventory일 뿐 v0.2.0 최종 승인값으로 간주하지 않는다.

## 2. Hosted Supabase Auth read-only verifier

Repository command:

```bash
pnpm ops:verify-auth-config
```

직접 실행:

```bash
node tooling/supabase/verify-auth-config.mjs
```

필수 입력:

```text
SUPABASE_ACCESS_TOKEN
SUPABASE_PROJECT_REF
MEMBER_URL 또는 MEMBER_DOMAIN
OPS_URL 또는 OPS_DOMAIN
PUTDUK_AUTH_REDIRECT_URLS
```

검증기는 Supabase Management API의 아래 endpoint를 **GET-only**로 호출한다.

```text
GET /v1/projects/{project_ref}/config/auth
```

판정 대상은 URL configuration에 필요한 다음 두 필드뿐이다.

- `site_url`
- `uri_allow_list`

검증 원칙:

- Production project ref가 `gaugwamwceqdnqdqrxqg`와 다르면 FAIL
- member / ops origin은 서로 달라야 함
- 두 origin 모두 HTTPS
- member / ops origin에는 path, query, hash가 없어야 함
- `site_url`은 final member origin과 정확히 일치해야 함
- redirect allow-list는 운영자가 승인한 `PUTDUK_AUTH_REDIRECT_URLS`와 exact-set 일치해야 함
- 승인 목록의 redirect는 member 또는 ops origin에만 속해야 함
- global wildcard `*` 금지
- hostname wildcard 금지
- query/hash 포함 redirect 금지
- 누락 또는 예상 밖 redirect가 하나라도 있으면 FAIL
- access token 또는 Auth config 원문 전체를 출력하지 않음

이 verifier에는 `PATCH` / `POST`가 없으며 Production 설정을 변경하지 않는다.

## 3. Password reset redirect 주의점

현재 static app의 password reset 호출은 다음 형태다.

```text
resetPasswordForEmail(email, { redirectTo: window.location.href })
```

따라서 reset 요청 시점의 path가 달라질 수 있다. Supabase Auth redirect allow-list는 `redirectTo`와 일치해야 하며, Supabase는 production에서 가능한 한 정확한 redirect URL path를 권장한다.

v0.2.0 cutover에서 선택 가능한 안전한 처리 원칙:

1. 최종 앱 코드가 reset destination을 고정 경로로 바꾸면 그 정확한 URL만 allow-list에 등록한다.
2. 이번 release에서 현재 `window.location.href` 동작을 유지해야 한다면, final member/ops origin 아래 필요한 path 범위를 운영자가 명시적으로 승인하고 `PUTDUK_AUTH_REDIRECT_URLS`에 기록한다.

어느 경우에도 임의의 다른 hostname을 허용하거나 전역 wildcard를 사용하지 않는다.

## 4. Auth cutover 실행 순서

final mapping 승인 이후에만 진행한다.

1. final member / ops origin 확정
2. 실제 password-reset destination 정책 확정
3. `PUTDUK_AUTH_REDIRECT_URLS` 확정
4. 현재 Hosted Auth config GET snapshot 확보
5. 승인된 값으로 Auth config 변경
6. 즉시 `node tooling/supabase/verify-auth-config.mjs` 실행
7. FAIL이면 Edge/static cutover로 진행하지 않음
8. recovery/rollback을 위해 변경 전 `site_url` / `uri_allow_list` 값을 민감정보가 아닌 운영 snapshot으로 보존

현재 repository에는 Auth config를 자동 PATCH하는 release command를 넣지 않는다. final mapping 승인 전에 URL configuration이 우발적으로 변경되는 것을 피하기 위해 write와 verify를 분리한다.

## 5. Edge rollback 문제와 수정 계약

기존 rollback workflow는 target SHA에 특정 managed Edge Function 디렉터리가 없으면 해당 함수를 `skip`했다.

이 방식은 신규 함수가 Production에 배포된 뒤 과거 SHA로 rollback할 때 신규 함수가 계속 ACTIVE로 남는 partial rollback을 만들 수 있다.

예:

- current release: `member-task-detail`, `admin-work-asset` 배포
- target rollback SHA: 두 함수가 아직 존재하지 않음
- 구 방식: 기존 7개만 재배포, 신규 2개는 Production에 잔존

이 동작은 더 이상 허용하지 않는다.

## 6. Fail-closed Edge rollback

Repository tool:

```bash
node tooling/supabase/rollback-edge.mjs --target-root <target-checkout>
```

기본 동작은 **DRY RUN**이다.

계약:

- 관리 대상은 repository `EDGE_FUNCTIONS` 목록으로 제한
- remote function inventory를 먼저 조회
- target SHA에 없는데 Production에 배포된 managed function이 있으면 기본적으로 exit 2
- 이 상태에서는 어떤 함수도 재배포/삭제하지 않음
- 실제 적용은 `--apply`가 있어야만 가능
- target에 없는 managed function 삭제는 추가로 `--delete-absent`를 명시해야만 가능
- unmanaged function은 삭제 대상에 포함하지 않음
- 적용 후 모든 managed function을 `ACTIVE` 또는 `ABSENT` 기대상태로 다시 reconciliation

예시 dry run:

```bash
node tooling/supabase/rollback-edge.mjs --target-root rollback-target
```

누락 managed function 삭제까지 명시적으로 승인한 실제 rollback:

```bash
node tooling/supabase/rollback-edge.mjs \
  --target-root rollback-target \
  --apply \
  --delete-absent
```

`supabase functions delete`는 Supabase CLI의 공식 Edge Function 삭제 명령이며, workflow에서는 non-interactive 실행을 위해 CLI global `--yes`를 사용한다.

## 7. Workflow rollback gate

`.github/workflows/rollback.yml`은 다음을 요구한다.

- full 40-character target commit SHA
- Production project ref 일치
- current rollback tooling과 target SHA를 서로 다른 checkout에 유지
- 먼저 dry-run plan 실행
- `delete_absent_functions=false`가 기본
- target에 없는 managed function이 Production에 남아 있으면 삭제 승인 없이는 적용 단계 진입 불가
- `delete_absent_functions=true`일 때만 `--delete-absent` 전달
- Edge 적용 후 상태 reconciliation

DB migration은 자동 reverse하지 않는다. DB rollback은 데이터 손상 위험 때문에 별도 forward-fix migration 절차를 사용한다.

Auth config와 Supabase secrets 역시 Edge rollback이 자동으로 되돌리지 않는다. 따라서 release 직전 URL config / CORS secret의 이전 상태 snapshot이 별도로 필요하다.
