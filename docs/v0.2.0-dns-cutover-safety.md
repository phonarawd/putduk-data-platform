# v0.2.0 DNS / Cloudflare Cutover Safety

기준일: 2026-09-22 KST

이 문서는 v0.2.0 release가 Cloudflare Pages 배포와 DNS 변경을 혼동하지 않도록 경계를 고정한다.

## 1. 현재 상태

- final member origin: **UNRESOLVED**
- final ops origin: **UNRESOLVED**
- old-origin redirect/recovery policy: **UNRESOLVED**
- Production DNS mutation in this validation phase: **0**
- mail DNS mutation in this validation phase: **0**

기존 `app.hiptk.app` / `ops.hiptk.app` 및 `putduk.kr` 계열 값은 현재 inventory일 뿐 v0.2.0 최종 launch target으로 간주하지 않는다.

## 2. Release automation의 DNS 경계

현재 repository의 static release 실행 경로는 다음 파일들이다.

- `.github/workflows/release.yml`
- `scripts/automation/release.mjs`
- `tooling/cloudflare/domain-cutover-audit.mjs`
- `tooling/cloudflare/verify-deployment.mjs`
- `functions/_middleware.js`
- `dist/_headers`
- `dist/_redirects`

전수 확인 결과 이 경로에는 다음 DNS write 수단이 없다.

- Cloudflare REST `.../zones/.../dns_records` 호출
- `wrangler dns` 명령
- `cloudflare dns` 명령
- DNS record create/update/delete 명령

`.github/workflows/release.yml`은 `pnpm release:deploy`를 실행한다. 이 명령이 연결하는 `scripts/automation/release.mjs`가 `domain-cutover-audit.mjs --require-target`와 repository 검증을 수행하며, static Production 반영은 **Cloudflare Pages Git Integration**에 맡긴다. workflow 자체가 DNS record를 생성·수정·삭제하지 않는다.

`tooling/cloudflare/verify-deployment.mjs`는 배포된 member/ops URL의 HTTP 응답과 HTML/config/header 상태를 확인하는 verifier다. DNS record를 변경하지 않는다.

`tooling/cloudflare/domain-cutover-audit.mjs`는 최종 member/ops origin과 repository literal/config를 검사하는 audit다. DNS record를 변경하지 않는다.

`functions/_middleware.js`는 요청 host/path에 따른 redirect/recovery routing만 수행한다. DNS provider API를 호출하지 않는다.

`dist/_redirects`의 현재 규칙은 `/admin /admin/ 301` 한 줄이며 DNS 설정과 무관하다.

## 3. 기존 DNS 유지 정책

새 member/ops 도메인의 다음 항목이 모두 준비되기 전에는 기존 Production 도메인/DNS를 제거하거나 덮어쓰지 않는다.

1. final member/ops mapping 승인
2. 새 static deployment 준비
3. Supabase Auth `site_url` / redirect allow-list 준비 및 read-only 검증
4. `PUTDUK_ALLOWED_ORIGINS` 준비
5. Phase 1 + Edge 9-function release gate 준비
6. rollback target / Edge rollback dry-run 검증
7. 새 origin HTTP/domain smoke 계획 준비

즉 새 도메인 cutover가 실패해도 기존 member/ops origin을 recovery path로 유지할 수 있어야 한다.

## 4. Mail DNS는 release 범위 밖

v0.2.0 web/domain cutover 작업은 다음 mail-delivery DNS를 변경하지 않는다.

- MX
- SPF
- DKIM
- DMARC
- Resend 또는 다른 메일 공급자의 verification / sending DNS records

이 항목은 web member/ops origin cutover와 분리한다. 별도의 명시적 메일 도메인 작업 없이 삭제·교체·재생성하지 않는다.

Cloudflare DNS 변경이 나중에 필요해지더라도 web hostname record만 대상으로 범위를 좁히고, 기존 mail-related record는 사전 snapshot과 diff로 보존 여부를 확인해야 한다.

## 5. Final DNS cutover 전 필수 snapshot

실제 DNS 변경을 승인하기 직전에 다음을 별도 운영 snapshot으로 보존한다.

- 기존 member hostname record type/name/target/proxy 상태
- 기존 ops hostname record type/name/target/proxy 상태
- TTL / proxy 상태
- Pages custom domain 연결 상태
- 기존 recovery origin
- 기존 Auth `site_url` / `uri_allow_list`
- 기존 `PUTDUK_ALLOWED_ORIGINS`
- 동일 zone의 MX/SPF/DKIM/DMARC/메일 공급자 records 존재 여부

민감 secret 값은 snapshot에 기록하지 않는다.

## 6. DNS cutover 실행 원칙

final mapping 승인 전에는 DNS write를 하지 않는다.

승인 후에도 다음 순서를 따른다.

1. 새 Pages/custom-domain target이 준비됐는지 확인
2. Auth/CORS 값과 member/ops hostname이 일치하는지 확인
3. 기존 DNS snapshot 확보
4. web hostname record만 명시적으로 변경
5. member/ops HTTPS 및 routing fingerprint smoke
6. Supabase Edge CORS/auth smoke
7. password-reset redirect smoke
8. 실패 시 기존 web hostname target으로 복구
9. mail DNS unchanged diff 확인

DNS 변경과 application release를 한 번의 불투명한 자동화로 묶지 않는다.

## 7. Repository regression gate

`tests/unit/domain-dns-safety.test.mjs`는 release executable 경로에 다음 mutation signature가 들어오는 것을 막는다.

- `api.cloudflare.com/client/v4/zones`
- `/dns_records`
- `wrangler dns`
- `cloudflare dns`
- DNS record create/update/delete 계열 명령

또한 release entrypoint가 `pnpm release:deploy` → `domain-cutover-audit.mjs --require-target` 검증 경로를 유지하고, workflow가 Cloudflare zone/API token을 직접 사용하지 않는 계약을 확인한다.

이 테스트는 DNS provider 상태를 검증하는 테스트가 아니라 **repository release path가 조용히 DNS mutation 기능을 얻지 못하게 하는 guard**다.

실제 DNS 상태는 final mapping 승인 이후 provider-side read-only inventory/snapshot으로 별도 확인해야 한다.

## 8. CI-independent evidence

2026-09-22 검증 세션에서 current branch의 release-critical 파일을 직접 재확인했다.

- `.github/workflows/release.yml`: Pages Git Integration 안내, 직접 DNS write 없음
- `scripts/automation/release.mjs`: repository/domain verification only, 직접 Cloudflare API deploy 없음
- `tooling/cloudflare/domain-cutover-audit.mjs`: local file/env audit only
- `tooling/cloudflare/verify-deployment.mjs`: HTTP GET/read-only deployment verification
- `functions/_middleware.js`: request routing/recovery only
- `dist/_redirects`: `/admin /admin/ 301`
- `dist/_headers`: HTTP security/cache headers only

추가 repository code search에서 `api.cloudflare.com/client/v4/zones`, `/dns_records`, `wrangler dns` mutation signature가 발견되지 않았다.

새 guard 자체는 Node `22.16.0` 환경에서 문법 검사 및 로컬 mirror 실행을 확인했다.

```text
node --check tests/unit/domain-dns-safety.test.mjs   PASS
node --test tests/unit/domain-dns-safety.test.mjs    2/2 PASS
```

이 실행은 Node 24 release PASS로 승격하지 않는다. 공식 release runtime은 `.nvmrc`의 Node 24 범위를 따른다.

## 9. STOP 조건

다음이 unresolved인 동안 DNS/custom-domain Production write는 시작하지 않는다.

- final member origin
- final ops origin
- old-origin redirect/recovery policy
- final Supabase Auth URL policy
- final Edge CORS origins
- password-reset destination policy
- provider-side current DNS snapshot

GitHub Actions 성공/실패는 이 DNS 승인 조건을 대체하지 않는다.
