# 0. 현재 패치 최우선 범위 고정

아래 범위는 이 문서의 다른 장기 개선 항목보다 **현재 작업에서 우선 적용되는 실행 경계**다.

```text
현재 패치에 포함
1. 비로그인 사용자 전용 랜딩페이지 추가
2. 로그인 회원은 기존 작업실 홈을 그대로 표시
3. 회원 홈 지갑 금액 글자 대비 수정
```

```text
현재 패치에서 제외·변경 금지
1. FOMO 피드와 이름 풀
2. 활동 인원 계산과 표시 수치
3. 자리 소진 연출과 타이머
4. crowd_min / crowd_max / burn_per_minute
5. 봇 관련 동작과 데이터 생성 방식
6. crew_pulse 및 관련 DB 구조·데이터
7. 관련 Supabase 함수와 Edge Function
8. 관련 어드민 화면·설정·제어
```

이 제한은 **현재 진입 구조 및 지갑 가독성 패치에만 적용되는 변경 금지선**이다. 이 문서 후반의 실제 데이터 기반 FOMO 장기 목표는 폐기하지 않지만, 별도 작업 지시와 승인 없이는 착수하지 않는다.

`dist/assets/app.js`처럼 랜딩·회원 홈·FOMO 로직이 한 파일에 섞여 있으면 파일 전체를 잠그는 대신 **FOMO 관련 함수·상수·타이머·쿼리·렌더 블록을 변경 금지 영역으로 취급**한다. 현재 패치의 diff에는 FOMO 및 봇 관련 동작 변경이 없어야 한다.

# 0. 절대 목표

퍼뜩은 한국의 20대~70대 남녀 누구든, 직장인·사업자·대학생·주부·육아맘·경력단절자·취업준비생을 불문하고 **설명서를 읽지 않아도 휴대폰 하나로 업무를 선택하고 수행하고 제출하고 정산 상태를 이해할 수 있는 온라인 업무 플랫폼**이어야 한다.

회원에게는 복잡함을 숨기고, 운영자에게는 모든 핵심 운영값을 쉽게 제어할 수 있게 한다.

## 절대 금지

- 같은 업무의 회사명·제목만 바꾼 복사 업무 양산
- 실제 근거 없이 사람 수·완료 수·예산·잔여 자리·마감시간을 실제처럼 표시
- 첫 체험 전에 입금/업무잔액을 과도하게 강조
- 회원/어드민 화면에 `5M`, `9M`, `1K` 같은 축약 금액 표시
- 회원/어드민 화면에 개발용·테스트용·DB/API/RPC/slug/path/seed 같은 용어 노출
- 토스트를 단순 이동·닫기·단계 완료마다 남발
- 120개 업무를 한 번에 DOM에 모두 그려 저사양 모바일에서 렉 발생
- 고액 입금 자체를 이유로 대기기간·숙성기간을 강제
- 원금 출금 자체를 이유로 자동 등급 강등/혜택 박탈

# 1. 재전수조사에서 확인된 현재 상태

## 1.1 온보딩 순서 문제

현재 `queueOnboarding()`은 신규 회원에게 PWA 설치 안내를 먼저 띄우고 그 다음 지원금 안내를 보여준다.

현재 순서:

```text
가입/로그인
→ 홈 화면 설치 안내
→ 가입 지원금 안내
→ 일반 화면
```

최종 순서에서는 완전히 바꾼다.

```text
가입
→ 가입 축하 + 퍼뜩이 지원한 첫 업무
→ 즉시 체험
→ 제출
→ 검수/첫 수당 경험
→ 일반 업무 소개
→ 필요한 순간에만 업무잔액 설명
→ 첫 일반 업무
→ 첫 가치 경험 뒤 앱 설치 안내
```

**첫 온보딩에 `왜 업무잔액이 필요한가요?`를 강제로 넣지 않는다.**

회원이 아직 퍼뜩의 가치를 경험하기 전에는 `입금`, `보증`, `원금`을 전면 메시지로 사용하지 않는다.

---

## 1.2 현재 업무가 실제로 충분히 다양하지 않음

Production 공개 operator 업무는 현재 13개다.

재조사 결과:

- 공개 업무 13개
- 서로 다른 `question_prompt_ko`: **1개**
- 서로 다른 보기 조합: **1개**
- `commerce_catalog` 계열: 2개
- 그 외 검수 계열: 11개

즉 현재 DB의 이름·회사·금액은 다르지만 실제 회원 수행 구조는 사실상 **상품정보 입력형 / 라벨·전표 대조형** 두 흐름으로 축약된다.

120개 확장은 현재 node를 이름만 바꿔 복제하는 방식으로 절대 진행하지 않는다.

---

## 1.3 현재 FOMO는 가상 연출 기반

현재 회원 코드에는:

- 가명 이름 풀
- 파트너 랜덤 선택
- `crowd_min ~ crowd_max` 파동 계산
- `burn_per_minute`로 자리 가상 소진

구조가 존재한다.

현재 Production `crew_pulse` 기준값은:

```text
표시 켜짐: true
활동 인원 최소: 160
활동 인원 최대: 200
분당 자리 소진: 17
```

최종 구조에서는 이 가상 카운터를 제거한다.

운영자는 **표시 상한을 직접 정할 수 있지만 실제값을 넘겨 표시할 수 없다.**

```text
회원에게 표시되는 숫자 = min(실제 집계값, 운영자 표시 상한)
```

업무의 하루 최대 자리 자체는 운영자가 직접 정하므로, 실제 남은 자리 숫자의 시작 최대값도 운영자가 제어한다.

---

## 1.4 토스트가 과다하고 구현이 분산돼 있음

현재 `dist/assets/app.js`에는 50곳 이상의 `showToast()` 사용 지점이 있다.

예:

- 로그인 성공
- 화면 닫기
- 검수 화면 닫기
- 추천코드 복사
- 각 검수 항목 1건 완료
- 앱 설치
- 업무 시작
- 제출
- 각종 저장

또 `phase4-finance-wiring.js`는 별도의 자체 toast 함수를 가지고 있다.

즉 현재는 토스트 정책이 한 곳에 통제되지 않는다.

최종 구조에서는 **토스트 엔진을 하나로 통합**하고, 특정 행동에만 허용한다.

Production `notifications`도 재조사 결과:

```text
전체 41건
테스트/검증 계열 문구 포함 24건
```

회원 화면에는 일부 sanitize가 존재하지만 canonical 데이터는 정리가 필요하다.

## 1.5 120개 확장 전에 성능 구조 수정 필요

현재 회원 업무 목록:

```javascript
memberCatalogNodes().map(renderNodeCard).join('')
```

즉 보이는 업무를 한 번에 전부 DOM으로 만든다.

어드민 업무 목록도 모든 row를 한 번에 렌더한다.

추가로 현재 여러 후처리 스크립트에 subtree `MutationObserver`가 있다.

- member UIUX observer
- growth UI observer
- brand runtime observer
- finance form observer
- admin UI observer

어드민 UI observer는 재귀 증폭 방지가 이미 적용돼 있어 유지할 가치가 있지만, 120+ 업무 확장 전에는 관찰 범위를 더 줄인다.

또 `phase3-admin-wiring.js`는 회원 페이지를 25명씩 표시하면서도 내부적으로는 서버에서 100명씩 최대 100번, 즉 최대 10,000명을 브라우저로 받아온 후 페이지를 나누는 구조다. 현재 회원 수에서는 체감이 작아도 확장 구조로는 교체 대상이다.

## 1.6 현재 모션 엔진의 좋은 부분

`motion-runtime.js`는 다음을 이미 지원한다.

- `prefers-reduced-motion`
- 하드웨어 코어 수
- device memory
- save-data
- 탭 hidden 상태
- DPR 상한

이 품질 감지 구조는 유지한다.

최종 패치는 애니메이션을 늘리는 것이 아니라 **의미 있는 순간에만 사용하고, 비활성 화면에서는 완전히 멈추는 방향**으로 진행한다.

## 2.2 접속 상태별 최상단 진입 구조

`app.hiptk.app`의 첫 화면은 브라우저가 기억하는 가입 이력이 아니라 **현재 로그인 세션 유무**로 결정한다.

```text
app.hiptk.app 접속
├─ 로그인 세션 없음
│  └─ 전용 랜딩페이지
└─ 로그인 세션 있음
   └─ 기존 회원 작업실 홈
```

### 비로그인 사용자

비로그인 상태에서는 기존 회원 작업실을 먼저 보여주지 않는다. 퍼뜩을 5초 안에 이해할 수 있는 전용 랜딩페이지를 표시한다.

첫 화면 기준 문구:

```text
공고를 찾지 마세요.
오늘 할 일을 고르세요.

기다리는 지원 대신,
지금 가능한 온라인 업무를 확인하고 바로 시작하세요.

[무료로 시작하기]
[로그인]
```

랜딩페이지 기본 순서:

```text
퍼뜩 소개
→ 실제로 하는 업무 예시
→ 업무 선택·수행·제출·검수·수당 확인 흐름
→ 장점
→ 회원가입 / 로그인
```

공개 업무 일부는 읽기 전용 미리보기로 표시할 수 있다. 단, 실제 업무 시작 버튼과 회원 전용 데이터는 로그인 후에만 활성화한다. 미리보기 수치와 업무 정보는 실제 공개 데이터만 사용한다.

### 로그인 회원

로그인 세션이 있으면 랜딩페이지를 건너뛰고 현재 회원 작업실 홈으로 바로 이동한다. 기존 작업실의 다음 영역은 현재 패치에서 그대로 유지한다.

- 상단 FOMO 영역
- 현재 활동 인원
- 자리 소진
- 회원 카드
- 업무 매칭
- 최근 수당 흐름
- 지갑
- 다음 업무 단계
- 추천 업무
- 최근 업무

회원가입 완료 후 로그인 세션이 생성되면 회원 작업실로 이동한다. 이미 가입한 회원도 로그아웃 상태에서는 랜딩페이지를 보고, `로그인`을 누른 뒤 기존 작업실로 이동한다.

### 렌더링 원칙

- 인증 상태 확인 전 회원 작업실이나 랜딩을 잘못 먼저 그리지 않는다.
- 세션 확인 중에는 짧은 중립 로딩 화면을 사용해 화면 깜빡임과 회원 데이터 노출을 막는다.
- 인증 성공 후 기존 회원 홈 초기화 순서와 FOMO 실행 순서는 변경하지 않는다.
- 랜딩 CTA는 회원가입·로그인 경로에만 연결한다.
- 랜딩 미리보기는 업무 실행·지갑·개인 알림 API를 호출하지 않는다.

## 2.3 회원 홈 지갑 금액 대비

현재 Premium CSS의 밝은 지갑 배경과 기존 흰색 금액 글자가 겹쳐 금액이 보이지 않는 문제를 현재 패치에서 수정한다.

적용 기준:

```css
.wallet-card .wallet-slot strong {
  color: var(--text);
}

.wallet-card .wallet-slot .ui-lead {
  color: var(--muted);
}

.wallet-card .wallet-slot small {
  color: var(--muted);
}
```

지원금·업무잔액·출금 가능 금액은 밝은 배경에서 짙은 검정 또는 녹색 계열로 명확하게 보여야 한다. 데스크톱과 모바일, 일반·포커스·선택 상태에서 모두 WCAG AA 수준의 대비를 확인한다.

## 2.4 로그인·회원가입 화면 최종 규격

로그인 화면은 입력 항목이 적으므로 작고 빠르게 유지한다. 회원가입은 입력·약관·동의 항목을 담을 수 있도록 로그인보다 넓게 구성한다.

### 데스크톱

```text
로그인 모달    480~520px
회원가입 모달  680~760px
```

- 랜딩 배경 위에 dimmed overlay와 중앙 모달을 사용한다.
- 로그인에는 이메일, 비밀번호, 비밀번호 재설정, 로그인 버튼만 우선 표시한다.
- 회원가입에는 필수·선택 구분, 비밀번호 확인, 이용약관, 개인정보 동의, 선택 알림 동의를 명확히 구분한다.
- 로그인과 회원가입을 같은 작은 폭으로 강제하지 않는다.
- 모달은 focus trap, ESC 닫기, 배경 스크롤 잠금, 오류 발생 시 첫 오류 필드 이동을 지원한다.

### 모바일

```text
로그인    화면 폭 대부분을 사용하는 sheet
회원가입  거의 full-screen인 가입 화면
```

- 430px 이하에서는 고정 폭 모달을 사용하지 않는다.
- 모바일 회원가입은 상단 뒤로가기와 제목, 스크롤 가능한 본문, 안전영역을 고려한 하단 제출 버튼을 사용한다.
- 소프트 키보드가 열려도 입력 필드와 주 CTA가 가려지지 않아야 한다.
- 로그인 성공 시 인증 화면을 닫고 기존 회원 작업실을 한 번만 초기화한다.

## 2.5 랜딩 이용 현황 — 운영자 관리 + 검증 가능한 수치

랜딩에는 이용 현황을 표시할 수 있다. 값의 출처는 실제 자동 집계 또는 운영자가 근거를 확인한 확정값으로 제한한다.

표시 가능 항목:

- 실제 누적 방문자 수
- 실제 누적 가입 회원 수
- 최근 기준시간 실제 활동 회원 수
- 오늘 실제 완료 업무 수
- 실제 지급된 수당 합계
- 운영 목표 수치

운영자 메뉴명은 **랜딩 이용 현황**으로 한다.

운영자 입력 항목:

```text
표시 항목
표시 숫자
수치 유형: 실제 자동 집계 / 운영자 확정값 / 목표
숫자 출처
집계 기준일
공개 여부
표시 순서
```

회원 화면에서는 `누적`, `최근 30분`, `오늘`, `목표`, `기준일`을 정확히 표시한다. 운영자 확정값은 근거와 기준일이 있어야 공개할 수 있다. 실제 활동자처럼 보이는 임의 봇 숫자, 무작위 증감, 근거 없는 가입자 수는 사용하지 않는다.

숫자 애니메이션은 저장된 공개값 또는 실제 집계값이 변경될 때만 짧게 실행한다. 장식용 랜덤 카운트업·다운은 사용하지 않는다.

내부 구조는 기존 FOMO 테이블과 분리한다.

```text
landing_metric_settings
landing_metric_snapshots
landing_content_audit_logs
```

- 랜딩 공개 읽기 API는 공개 승인된 숫자와 기준일만 반환한다.
- 관리자만 등록·수정·공개할 수 있다.
- 변경 전후 값, 변경자, 변경시각을 감사기록에 남긴다.
- 기존 `crew_pulse`, FOMO 계산, 이름 풀, 봇 설정과 연결하지 않는다.

## 2.6 랜딩 회원 후기 — 어드민 등록·검수·자동 순환

운영자는 어드민의 **랜딩 회원 후기** 메뉴에서 후기를 등록·수정·공개·숨김 처리할 수 있다.

운영자 입력 항목:

```text
작성자 표시명
후기 내용
완료 업무
후기 유형
업무 완료 확인
회원 공개 동의
표시 순서
공개 시작일·종료일
공개 상태
```

실제 회원 후기에는 완료된 업무 기록과 공개 동의를 연결한다. 이름은 `김○민`처럼 자동 마스킹한다. 실제 완료 기록이 연결된 경우에만 `업무 완료 확인` 배지를 표시한다. 운영자가 만든 설명용 문구는 실제 회원 후기로 섞지 않고 `이용 예시`라고 명확히 표시한다.

내부 구조:

```text
landing_reviews
landing_review_consents
landing_content_audit_logs
```

공개 API는 마스킹된 이름, 공개 후기, 공개 가능한 업무명, 배지 상태만 반환한다. 회원 ID, 연락처, 내부 업무 기록은 반환하지 않는다. 공개 스키마를 사용할 경우 RLS를 활성화하고, 공개 읽기 정책과 관리자 쓰기 권한을 분리한다.

### 후기 자동 스크롤

- 공개 기간 안의 후기만 노출한다.
- 같은 후기의 연속·동시 중복을 금지한다.
- 한 세션에서 가능한 한 모든 공개 후기를 순환한 뒤 다시 섞는다.
- 마우스 hover, 키보드 focus, 터치 조작 중에는 자동 이동을 멈춘다.
- 사용자가 이전·다음 후기를 직접 탐색할 수 있어야 한다.
- `prefers-reduced-motion`에서는 자동 스크롤을 끄고 정적 카드로 표시한다.
- 공개 후기가 3개 미만이면 자동 스크롤하지 않는다.
- 후기 수를 부풀리거나 존재하지 않는 수천 명의 사용 경험을 생성하지 않는다.

## 2.7 로그인 회원 홈의 빈 상태 최적화

로그인 후 현재 회원 홈의 정보 순서는 유지한다.

```text
상태
→ 메인 업무 CTA + 사원증
→ 수당 흐름 + 지갑
→ 다음 단계
→ 추천 업무
→ 최근 업무
```

단, 데이터가 없는 신규 회원에게 큰 빈 카드와 빈 차트를 연속으로 보여주지 않는다.

### 추천 업무 없음

```text
오늘 추천 근무

현재 참여 가능한 업무가 없습니다.
새 업무가 열리면 이곳에 표시됩니다.

[업무 매칭 확인]
```

위 내용을 compact card로 표시하고 불필요한 최소 높이를 제거한다.

### 수당 기록 없음

수당 기록이 0건이면 큰 빈 차트를 생성하지 않는다.

```text
아직 수당 기록이 없어요.
첫 업무가 승인되면 여기에 수당 흐름이 나타납니다.
```

수당 기록이 한 건 이상 생긴 뒤에만 차트를 생성한다.

## 2.8 등급·혜택 페이지

- 데스크톱 로드맵은 좌측 절반에 제한하지 않고 전체 콘텐츠 폭을 사용한다.
- 현재 등급과 다음 등급의 관계를 한 화면에서 읽을 수 있어야 한다.
- 잠금 등급도 이름·조건·진행 구조가 식별될 만큼 충분한 대비를 유지한다.
- 비활성 상태는 색과 아이콘으로 표현하되 텍스트 자체를 사라지게 하지 않는다.
- 모바일에서는 단계가 세로로 자연스럽게 이어지도록 한다.

## 2.9 지갑·내역·업무 매칭 빈 상태

- 지갑의 지원금·업무잔액·출금 가능 금액은 페이지와 홈에서 같은 시각 규칙을 사용한다.
- 제목은 muted보다 한 단계 진하게, 금액은 가장 강한 대비, 아이콘은 emerald, 설명은 muted로 표시한다.
- 사용불가 상태만 카드 또는 설명의 opacity를 낮추며 금액 자체에는 opacity를 적용하지 않는다.
- 최근 지갑 내역, 업무 내역, 공개 업무가 없을 때 카드 높이를 콘텐츠에 맞게 줄인다.
- 빈 페이지 중앙에 작은 문구만 띄우지 않고 설명과 다음 행동을 가진 compact panel을 제공한다.

업무 매칭 빈 상태:

```text
현재 참여 가능한 업무가 없습니다.
새 업무가 공개되면 이 화면에 바로 표시됩니다.

[새로 확인]
```

## 2.10 출금 모달

- 현재 업무잔액, 현재 출금 가능 금액, 신청 후 잔액을 일러스트보다 먼저 읽을 수 있게 한다.
- 상단 일러스트 높이는 현재보다 약 30~40% 줄인다.
- 핵심 금액에는 opacity를 적용하지 않는다.
- 데스크톱에서는 기존 모달 구조를 유지한다.
- 모바일에서는 `취소`와 `이해하고 신청` CTA 영역을 안전영역을 고려해 하단에 안정적으로 배치한다.
- 버튼 고정 시 본문 마지막 내용이 버튼 뒤에 가려지지 않도록 하단 여백을 확보한다.

## 2.11 현재 UI 패치 우선순위

1. 비로그인 랜딩 / 로그인 작업실 AUTH 분기
2. 지갑 금액과 연한 텍스트 가독성
3. AUTH 판별 전 회원 화면 flash 방지
4. 빈 차트·추천 업무·내역·지갑 내역 compact empty-state
5. 등급 페이지 데스크톱 폭과 잠금 대비
6. 출금 모달 일러스트 비중과 모바일 CTA
7. 로그인 520px / 회원가입 760px 정책 유지와 모바일 확장
8. 랜딩 이용 현황·후기 어드민 기능

# 3. 전환율 우선 신규회원 온보딩

## 3.1 가입 직후 — 돈 이야기를 먼저 하지 않는다

첫 화면:

```text
🎉 퍼뜩에 오신 걸 환영합니다

첫 업무는 퍼뜩이 지원해요.
지금 바로 한번 해보세요.

[첫 업무 시작]
```

작은 보조 문구:

```text
회원 부담 없이 첫 업무 흐름을 경험할 수 있어요.
```

이 시점에는:

- 입금
- 업무잔액
- 원금
- 고액 업무

을 메인 설명으로 보여주지 않는다.

## 3.2 첫 체험 업무

```text
퍼뜩 첫 업무
지원금 10,000원 사용
회원 부담 0원
완료 수당 +3,000원
예상 시간 30초

[업무 시작]
```

금액은 항상 `10,000원`, `3,000원`처럼 전체 원화 표기한다.

## 3.3 첫 업무 수행

화면은 한 행동씩만 요구한다.

```text
1 / 3
이 항목을 확인해 주세요.

[선택 A]
[선택 B]
```

진행 완료는 토스트가 아니라 화면 내부 진행률로 표시한다.

## 3.4 제출 직후

```text
업무를 제출했어요

이제 검수 결과만 기다리면 됩니다.

[작업실로 돌아가기]
```

## 3.5 첫 승인 — 첫 가치 경험

```text
✅ 첫 업무가 승인됐어요

완료 수당
+3,000원

출금 가능
3,000원

[다음 업무 보기]
```

숫자 이동 애니메이션은 이 순간에만 짧게 사용한다.

## 3.6 일반 업무잔액 설명은 이 뒤에 처음 등장

회원이 `다음 업무 보기`를 눌렀고 일반 업무를 선택하려 할 때만 설명한다.

```text
일반 업무는 이렇게 진행돼요

업무를 맡는 동안 필요한 금액만 잠시 보관됩니다.
정상 정산이 끝나면 같은 금액이 업무잔액으로 돌아오고,
완료 수당은 출금 가능 금액에 따로 추가됩니다.

[내게 가능한 업무 보기]
```

**초기 온보딩에 `왜 업무잔액이 필요한가요?` 페이지를 강제 삽입하지 않는다.**

FAQ에는 남기되 사용자가 궁금할 때 열도록 한다.

## 3.7 입금 설명은 사용자가 필요성을 느낀 순간에만

현재 잔액보다 큰 업무를 눌렀거나 `업무잔액 늘리기`를 눌렀을 때:

```text
업무잔액이 커지면 무엇이 달라지나요?

현재 업무잔액        50,000원
현재 가능한 최대 업무 50,000원

업무잔액 1,000,000원이 되면
1,000,000원급 공개 업무까지 바로 선택할 수 있어요.

[현재 가능한 업무 보기]
[업무잔액 늘리기]
```

## 3.8 앱 설치 안내 시점

PWA 설치는 첫 로그인 직후가 아니다.

권장 시점:

```text
첫 업무 제출 완료 이후
또는 첫 업무 승인 이후
```

문구:

```text
다음 업무를 더 빨리 확인하고 싶다면
퍼뜩을 홈 화면에 둘 수 있어요.

[홈 화면에 추가]
[나중에]
```

support_grant = 퍼뜩 체험 지원금
work_balance  = 일반 업무 보증 가능 잔액
available     = 출금 가능한 확정 수당/지급액

```text
업무 시작

허용한다.

출금 전 업무잔액 10,000,000원
출금 후 업무잔액  1,000,000원

출금 전 최대 업무 10,000,000원
출금 후 최대 업무  1,000,000원
```

이 차이를 출금 확인 화면에서 보여준다.

# 6. 120개 업무를 “진짜 서로 다른 업무”로 만드는 엔진

## 6.1 기존 방식 폐기

현재처럼:

```text
회사만 바꿈
제목만 바꿈
같은 질문
같은 보기
같은 수행화면
```

방식으로 node를 양산하지 않는다.

## 6.2 새로운 업무 구조

내부적으로 다음 구조를 만든다.

```text
work_templates
work_template_versions
work_orders
task_run_items
task_run_answers
```

회원/어드민에는 이 테이블명이나 기술 용어를 노출하지 않는다.

### 업무마다 반드시 다른 값

각 업무는 다음을 독립적으로 가져야 한다.

- 고유 업무 흐름 키
- 실제 목적
- 입력 데이터 종류
- 회원이 해야 하는 행동
- 제출 결과 형태
- 검증 방법
- 필요 단계 수
- 예상 시간
- 오류 메시지
- 완료 조건

### 공통 UI 부품 재사용은 허용

버튼·사진 보기·숫자 입력 같은 UI 부품은 재사용할 수 있다.

하지만 **업무 목적과 단계, 데이터, 판정 로직까지 같고 이름만 다른 업무는 금지**한다.

# 7. 120개 실제 업무 카탈로그

아래 120개는 이름만 다른 복제 업무가 아니라 서로 다른 입력/판정/결과를 갖는 업무로 구현한다.

## A. 택배·배송 운영 10종

완전히 같은 지문을 가진 두 업무가 있으면 CI/검증 단계에서 실패시킨다.

제목만 바꾼 복제품은 등록할 수 없다.

어드민에서 기존 업무를 복제하더라도 **복제본은 초안 상태이며, 실제 단계 또는 데이터 규칙을 바꾸기 전에는 공개할 수 없게 한다.**

# 9. 소액 → 고액 업무 경험 설계

금액이 높아질수록 단순히 같은 일을 더 적게 시키는 것이 아니라 **업무 성격을 바꾼다.**

## 소액

- 초보자용
- 단계 4~8개
- 단순 비교/입력
- 설명이 충분함

## 중간

- 단계 3~5개
- 표준화·분류·교차확인

## 고액

- 단계 1~3개
- 이미 정제된 데이터의 최종 판단
- 짧고 명확한 화면
- 책임도가 높은 최종 확인

## 초고액

- 지정된 고가치 데이터셋
- 소수 핵심 판단
- 운영자 배정 여부는 `requires_assign` 설정만 따른다

회원에게는 `돈을 많이 넣어서 수익이 높다`가 아니라 해당 업무의 실제 수당과 업무 내용을 그대로 보여준다.

# 11. FOMO 최종 구조 — 운영자 제어 + 실제 데이터

> **현재 패치 보호 규칙:** 이 장은 장기 리빌드 목표다. 비로그인 랜딩 및 지갑 대비 패치에서는 기존 FOMO·봇 구현, 표시 수치, 이름 풀, 타이머, DB, Supabase 함수, Edge Function, 어드민 제어를 수정하거나 마이그레이션하지 않는다. 실제 데이터 기반 교체는 별도 작업으로 승인된 경우에만 진행한다.

어드민 메뉴명은 `FOMO`가 아니라 **실시간 현황 표시**로 한다.

운영자가 조절:

- 실시간 현황 표시 켜기/끄기
- 활동 인원 표시 최대값
- 최근 완료 건수 표시 최대값
- 남은 자리 표시 최대값
- 최근 배정 표시 최대값
- 최근 몇 분을 집계할지
- 회원 이름 표시 여부
- 예산 잔액 표시 여부
- 업무 카드 강조 여부

실제 표시:

```text
표시값 = min(실제값, 운영자 상한)
```

예:

```text
실제 최근 활동 회원 37명
운영자 표시 최대 30명
→ 회원 화면 30명

실제 최근 활동 회원 7명
운영자 표시 최대 30명
→ 회원 화면 7명
```

운영자가 숫자를 크게 적었다고 실제보다 큰 값을 생성하지 않는다.

### 실제 FOMO 항목

- 오늘 남은 자리
- 최근 실제 업무 시작 수
- 최근 실제 승인 수
- 현재 실제 공개 업무 수
- 실제 검증된 남은 파트너 예산
- 실제 회원의 다음 최대 업무 해금

가짜 이름 풀과 가상 자리 소진 로직은 제거한다.

# 13. 토스트/알림 최종 규칙

## 13.1 토스트 엔진 하나만 사용

`app.js`와 별도 finance toast를 하나의 중앙 피드백 모듈로 합친다.

### 한 번에 하나만 표시

- 최대 동시 표시: 1
- 같은 이벤트 중복 방지
- 저우선 알림은 새 고우선 알림이 오면 교체
- 화면 이동 후 같은 성공토스트 재생 금지

## 13.2 토스트를 허용하는 경우

### 회원

- 업무 제출 서버 접수 성공
- 입금 신청 접수 성공
- 출금 신청 접수 성공
- 서버/네트워크 전체 오류
- 실시간으로 새 업무 배정이 들어왔고 현재 배정 화면을 보고 있지 않을 때
- 중요한 검수 결과가 실시간 도착했고 해당 화면을 보고 있지 않을 때

### 어드민

- 실제 저장 성공
- 승인/반려/완료 성공
- 전체 요청 실패

## 13.3 토스트를 쓰지 않는 경우

- 로그인 인사
- 로그아웃 완료
- 모달 열기/닫기
- 업무 화면 열기
- 업무 1건/2건/3건 단계별 완료
- 추천코드 복사
- 필드 유효성 검사
- 단순 탭 이동
- 앱 설치 버튼 누름
- 온보딩 단계 이동

이런 피드백은 버튼 옆 체크, 입력칸 아래 설명, 진행률, 화면 내 상태로 처리한다.

## 13.4 알림센터

알림센터는 지속 기록용이다.

- 업무 배정
- 검수 승인
- 재작업 요청
- 반려
- 입금 확인
- 출금 완료
- 중요 운영 공지

단순 UI 행동은 알림센터에 저장하지 않는다.

## 13.5 Production 테스트 알림 정리

현재 Production에 남아 있는 테스트/검증 계열 알림은 배포 전 별도 백업/확인 후 회원 노출 대상에서 제거한다.

앞으로 Production 어드민에는 `테스트 알림 보내기` 기능을 두지 않는다.

# 14. 애니메이션 최종 원칙

애니메이션은 장식이 아니라 **상태 변화 설명용**이다.

허용되는 핵심 장면:

1. 가입 완료
2. 첫 체험 업무 시작
3. 실제 업무 진행 중 핵심 단계 전환
4. 제출 완료
5. 검수 승인
6. 보증금 복귀 + 수당 추가
7. 더 큰 업무 해금

사용하지 않는 곳:

- 단순 목록 스크롤
- 어드민 테이블
- 입력 폼
- 반복 버튼
- 모든 카드의 상시 무한 애니메이션

저사양/절전/reduced-motion에서는 정적 화면 또는 최소 전환으로 자동 변경한다.

오프스크린 canvas는 즉시 정지하고 메모리에서 해제한다.

운영자가 정답 JSON, 이미지 경로, 내부 코드 등을 직접 입력하지 않는다.

네 가지 상태를 기본으로 사용한다.

# 18. 어드민 미리보기

운영자는 실제 돈을 바꾸지 않고 회원 화면을 미리 볼 수 있다.

프리셋:

```text
신규회원
50,000원 회원
300,000원 회원
1,000,000원 회원
10,000,000원 회원
지정업무가 있는 회원
진행 중 업무가 있는 회원
재작업 회원
```

단, 메뉴명은 `테스트`가 아니라 **화면 미리보기**다.

# 23. 완료 판정 기준

## 현재 P-1A 패치 완료 기준

- 비로그인 상태에서 전용 랜딩페이지가 표시됨
- 로그인 세션이 있으면 랜딩 없이 기존 회원 작업실이 표시됨
- 로그아웃한 기존 회원은 랜딩에서 로그인할 수 있음
- 가입 완료 후 생성된 세션으로 회원 작업실에 진입함
- 인증 확인 전 회원 데이터·좌측 메뉴·작업실 화면이 순간 노출되지 않음
- 데스크톱 로그인은 480~520px, 회원가입은 680~760px 범위임
- 모바일 로그인은 화면 폭 대부분, 회원가입은 거의 full-screen으로 동작함
- 지원금·업무잔액·출금 가능 금액이 홈과 지갑에서 명확히 보임
- 금액 자체에 opacity가 적용되지 않음
- 기록 없는 회원에게 빈 수당 차트를 생성하지 않음
- 추천 업무·지갑 내역·업무 내역·업무 매칭의 빈 상태가 compact panel임
- 등급 로드맵이 데스크톱 전체 콘텐츠 폭을 사용하고 잠금 단계가 식별됨
- 출금 모달 핵심 금액이 일러스트보다 우선되며 모바일 CTA 사용이 편리함
- FOMO 피드·이름 풀·활동 인원·자리 소진·타이머의 동작과 숫자가 변경되지 않음
- `crowd_min`·`crowd_max`·`burn_per_minute` 값이 변경되지 않음
- `crew_pulse`, 관련 Supabase 함수·Edge Function·기존 어드민 설정에 변경이 없음
- P-1A에는 데이터베이스 마이그레이션이 포함되지 않음

## P-1B 랜딩 운영 콘텐츠 완료 기준

- 랜딩 현황은 실제 집계값·근거 있는 운영자 확정값·명시된 목표 중 하나임
- 공개 수치에 기준 범위 또는 기준일이 표시됨
- 랜덤 봇 숫자나 근거 없는 가입자·활동자 수가 없음
- 어드민에서 랜딩 현황을 등록·수정·공개·숨김 처리할 수 있음
- 실제 회원 후기는 완료 업무·공개 동의와 연결됨
- 예시 문구는 `이용 예시`로 명확히 표시됨
- 같은 후기가 연속 또는 동시에 중복 노출되지 않음
- hover·focus·touch·reduced-motion에서 자동 스크롤이 안전하게 제어됨
- 공개 API가 회원 ID·연락처·내부 업무 기록을 반환하지 않음
- 랜딩 전용 테이블에 RLS와 최소권한 정책이 적용됨
- 모든 랜딩 현황·후기 변경에 감사기록이 남음
- 기존 회원 홈 FOMO·봇 코드와 데이터가 변경되지 않음
## 전체 MASTER 최종 완료 기준

다음이 전부 충족돼야 최종 완료다.


- 가입 직후 입금 설명을 강제하지 않음
- 첫 체험까지 1개의 주 CTA로 이동 가능
- 첫 체험 후 첫 수당 경험 전에는 고액 입금 압박 없음
- 120개 업무가 제목뿐 아니라 실제 workflow가 다름
- 120개 전부 사용자에게 실제 업무처럼 수행 가능
- 120개 업무 존재 시에도 최초 화면에 전부 DOM 생성하지 않음
- 저사양 모바일에서도 스크롤/터치 지연 없음
- 어드민에 개발/테스트/전문용어 없음
- 어드민에서 협력사·예산·업무·지원금·온보딩·FAQ·알림·실시간 표시를 제어 가능
- 모든 금액 `1,000,000원` 형식
- 토스트는 특정 서버 행동/중요 이벤트에만 표시
- 검수 한 건 완료마다 토스트가 뜨지 않음
- 가짜 활동 인원/가짜 사람 이름/가상 자리 소진 없음
- 운영자가 실시간 표시 최대값을 직접 설정 가능
- 실제 표시값은 운영자 상한과 실제값 중 작은 값
- 파트너 지급예산은 확인된 데이터만 회원에게 표시
- 원금 출금 자체로 자동 등급 강등 없음
- MAX BALANCE FIT 정상 동작
- `requires_assign`만 지정회원 전용의 최종 기준
- 모션은 저사양/reduced-motion에 자동 적응
- 공식 member/admin 도메인에서 E2E 완료
