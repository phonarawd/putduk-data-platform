# v0.2.0 Phase 6 — 출시 차단 E2E·아키텍처 게이트

## 범위

Phase 6는 새 기능을 추가하는 단계가 아니다. Phase 0 기준선에서 구현은 끝났지만 실제 브라우저/운영 계정 검증이 남아 있던 #3 로그인 원인 분류, #4 관리자 회원 상세·PII 권한, #12 로그아웃 상태 정리와 #15 백엔드 아키텍처를 출시 게이트로 고정한다.

## PII 권한 계약

회원 목록/상세 업무 권한은 `super_admin`, `member_support`가 사용할 수 있지만, `canRevealMemberPii()`는 `super_admin`만 원문 PII를 볼 수 있게 한다. 따라서 `member_support`가 회원 상세를 열 수 있다는 사실과 전체 휴대폰 번호를 볼 수 있다는 사실은 동일하지 않다. UI도 `pii_access`에 따라 “전체 휴대폰 번호 표시 중” 또는 “전체 번호는 최고관리자만 볼 수 있습니다” 안내를 표시한다.

실제 전화번호 값 자체는 Playwright assertion이나 실패 로그에 넣지 않는다.

## Live E2E side-effect 계약

`release-live.spec.ts`는 Production의 돈·업무·배정·검수 상태를 변경하는 테스트가 아니다. 아래 사업 상태 mutation은 live release validation에서 금지한다.

- 지갑 잔액 입금/차감
- ledger 지급/정산 기록 생성·변경
- 입금/출금 승인·완료·거절
- 업무 시작/제출/검수/승인/반려
- task assignment 생성·변경
- 회원 등급·지원금·추천보상 변경
- MASTER 120 공개/활성화

다만 인증과 보안 감사를 검증하는 과정에서 아래 운영 기록은 정상적인 side effect가 될 수 있다.

- Supabase Auth 로그인/로그아웃에 따른 session/auth 기록
- 관리자 상세 조회 시 서버의 권한 확인 기록
- `super_admin`이 원문 PII를 실제 열람한 경우 `putduk_admin_append_audit`를 통한 `회원 개인정보 열람` 감사로그

특히 `getMember()`는 `super_admin`만 `pii_access=true`로 원문 PII를 반환하고, 해당 열람은 감사로그를 남기는 것이 보안 계약이다. 따라서 live admin E2E를 “Production write 0”이라고 표현하지 않는다. 정확한 기준은 **사업 상태 mutation 0, 인증/보안 감사 side effect만 허용**이다.

`member_support`는 회원 상세 접근은 가능하지만 `pii_access=false`, `pii_masked=true` 상태를 유지한다. 어떤 역할로 실행하더라도 실제 PII 값 자체를 assertion, screenshot 설명, 실패 메시지 또는 테스트 로그에 출력하지 않는다.

관리자 live gate는 회원 목록의 첫 번째 행을 임의로 열지 않는다. 반드시 `PUTDUK_E2E_MEMBER_PUBLIC_ID`로 전용 테스트 회원의 사원번호를 지정하고, 회원 검색 결과에서 해당 사원번호가 포함된 행만 열어야 한다. 이 값이 없으면 관리자 live gate는 SKIP한다.

## 실행

일반 Phase 6 브라우저 게이트:

```bash
pnpm test:e2e:release
```

운영/전용 계정 live gate까지 실행하려면 저장소에 값을 커밋하지 말고 실행 환경에만 아래 값을 넣는다.

```text
PUTDUK_TRIAL_EMAIL
PUTDUK_TRIAL_PASSWORD
PUTDUK_ADMIN_EMAIL
PUTDUK_ADMIN_PASSWORD
PUTDUK_E2E_MEMBER_PUBLIC_ID
```

`PUTDUK_E2E_MEMBER_PUBLIC_ID`는 관리자 live gate가 열어도 되는 전용 테스트 회원의 사원번호다. 운영자 자격증명만 있고 이 값이 없으면 관리자 상세 검증은 실행하지 않는다.

필요하면 대상 주소만 다음 환경변수로 덮어쓴다.

```text
PLAYWRIGHT_MEMBER_URL
PLAYWRIGHT_ADMIN_URL
```

live gate는 로그인 세션을 만들고 관리자 PII 권한 경계를 확인하는 테스트이므로 운영에서 실행할 때는 반드시 전용 테스트 계정과 명시적으로 승인된 환경을 사용한다. `super_admin` 계정을 쓰면 지정된 테스트 회원 상세 열람 감사로그가 생성될 수 있음을 실행 증거에 함께 기록한다.

## 아키텍처 결론

현재 저장소는 정적 회원/운영자 앱(`dist`), Cloudflare 배포 설정, Supabase Auth/Postgres/Storage/Edge Functions를 중심으로 구성되어 있다. 루트 Render 서비스 정의가 없고 애플리케이션 런타임도 Express/Nest/Fastify 기반 별도 서버를 요구하지 않는다. 따라서 Phase 6에서 Render를 추가하거나 배포하지 않는다. 향후 장시간 작업, 전용 큐 워커, Supabase Edge 제약을 벗어나는 서버 런타임 요구가 생길 때 별도 ADR로 재검토한다.

## 현재 실행 상태

Phase 6 작성 환경에는 운영/전용 계정 자격증명을 주입하지 않는다. 따라서 live gate가 실제로 실행되지 않았다면 **SKIP/미실행**으로 기록하고 PASS라고 부르지 않는다. mock 브라우저 게이트 역시 Playwright 런타임을 실제 실행한 경우에만 PASS로 기록한다.
