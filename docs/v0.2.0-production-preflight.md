### CI-independent verification policy

GitHub Actions quota가 없어도 release gate를 검증할 수 있어야 한다. 현재 v0.2.0에서는 아래 증거를 우선 사용한다.

1. exact PR HEAD 파일 계약 검사
   - migration / deploy / rollback / JWT / domain fail-closed 계약을 HEAD SHA에 고정해 확인
2. Production Supabase read-only SQL
   - migration ledger
   - function / trigger definition과 dependency
   - DB integrity
   - MASTER 120 invariant
   - role / schema / table privilege
3. Supabase Management metadata
   - project health
   - development branch 부재
   - Edge Function ACTIVE / version / `verify_jwt`
   - Security Advisor 결과와 실제 권한 노출 여부 교차 확인
4. direct browser / HTTP smoke
   - member shell
   - ops shell
   - recovery origin
   - 로그인 UI 오픈 여부
   - 자격증명·돈·업무 mutation 없이 수행
5. runtime auth E2E
   - GitHub Actions가 아니라도 Node 24 + pnpm 12 + Playwright 1.63.0 조건이 맞는 독립 실행환경에서 실행 가능
   - 실행환경이 없으면 PASS로 쓰지 않고 `UNEXECUTED`로 유지

따라서 GitHub Actions의 quota/runner failure는 코드 failure로 해석하지 않는다. 반대로 위 독립 gate가 실패하면 Actions 상태와 무관하게 release를 중단한다.

### Phase 1 migration

Repository에는 다음 migration이 있다.

- `20260921102905_phase1_kst_day_boundary.sql`

Production `supabase_migrations.schema_migrations`에는 이 version/name 기록이 없다.

현재 Production `private.prepare_putduk_task_run()`은 **부분 적용 상태**다.

- 회원별 일일 횟수: KST `v_kst_day_start` 사용
- 노드별 일일 공급량: 아직 `date_trunc('day', v_now)` 사용
- node advisory lock date: 아직 session/UTC 기준 `to_char(v_now, 'YYYY-MM-DD')` 사용
- 따라서 노드 공급량과 회원 횟수가 동일 KST 자정 경계를 사용한다는 Phase 1 계약을 충족하지 않는다.

Repository migration과 Production function definition을 read-only로 대조했다. 업무 로직 차이는 KST 경계 정렬에 한정된다.

- KST day start를 업무 검증 초기에 1회 계산
- node advisory lock key도 `Asia/Seoul` 날짜 사용
- node daily cap count와 member daily count 모두 같은 `v_kst_day_start` 사용
- 기존 member block 내부의 늦은 `v_kst_day_start` 계산 제거
- 로그인/활성회원/배정/등급/동시업무/보상/잔액잠금/task assignment 갱신 로직은 유지
- function signature / `SECURITY DEFINER` / search path / trigger 연결은 유지

Production 의존성도 확인했다.

- `private.putduk_normalize_member_tier(text)` 존재
- `private.putduk_lock_stake(uuid,uuid,uuid,uuid)` 존재
- `public.task_runs`의 `prepare_putduk_task_run` BEFORE INSERT trigger 활성
- 같은 `task_runs`의 다른 BEFORE/AFTER trigger chain도 활성 상태이며 Phase 1은 해당 trigger를 재생성하거나 제거하지 않는다.

따라서 이 migration은 **Production Edge/static 배포보다 먼저 적용 및 검증되어야 한다.**

### Security Advisor interpretation

현재 Security Advisor의 `RLS enabled no policy` INFO 5건은 모두 `private.*` 테이블이다. 실제 privilege를 read-only로 교차 확인했다.

- `anon`: `private` schema USAGE 없음, 대상 table CRUD 없음
- `authenticated`: `private` schema USAGE 없음, 대상 table CRUD 없음
- `service_role`: 의도된 접근권한 보유

따라서 이 5건은 현재 외부 노출 release blocker가 아니라 hardening INFO로 분류한다.

`auth_leaked_password_protection` WARN은 별도 Auth hardening 항목으로 유지한다.

### Domain / Auth / CORS

최종 member/ops mapping은 아직 미확정이다.

- member origin: 미확정
- ops origin: 미확정
- Supabase Auth Site URL / Redirect URL: 최종값 미확정
- `PUTDUK_ALLOWED_ORIGINS`: 최종값 미확정

현재 repository / live inventory는 `app.hiptk.app` / `ops.hiptk.app` 중심으로 정렬되어 있고 recovery Pages origin도 응답한다. 그러나 이 inventory를 최종 승인 mapping으로 간주하지 않는다.

Supabase Auth Site URL / Redirect URL allow-list는 DB migration ledger로 검증할 수 있는 설정이 아니므로 최종 cutover 시 별도 Management/Auth 설정에서 확인한다.

`pnpm release:deploy`는 domain mapping이 명시되지 않으면 첫 단계에서 fail-closed한다.

## 2. Production 적용 순서

순서를 바꾸지 않는다.

1. **Final mapping 승인**
   - member origin
   - ops origin
   - old-origin redirect/recovery 정책
2. **Phase 1 migration preflight**
   - `ops:verify-migrations` 또는 동등한 read-only ledger check
   - 기존 11개 timestamp 차이는 `name_equivalent`로 분류
   - `github_unapplied`가 정확히 `20260921102905` 하나인지 확인
   - `remote_only_unexpected`가 없는지 확인
   - 대상 function/trigger 의존성 재확인
3. **Phase 1 migration 적용**
   - migration 파일 그대로 적용
   - 임의 SQL 조각만 복사해서 별도 적용하지 않는다.
4. **Post-migration read-only verification**
   - migration ledger에 `20260921102905` 존재
   - `private.prepare_putduk_task_run()` node lock key가 KST 날짜 사용
   - node daily cap과 member daily count가 같은 `v_kst_day_start` 사용
   - DB integrity gate 재실행
   - MASTER 120 draft/disabled 및 accidentally live 0 재확인
5. **Supabase Auth cutover 준비**
   - Site URL / Redirect URL allow-list에 승인된 member/ops 흐름 반영
6. **Supabase Edge CORS 준비**
   - `PUTDUK_ALLOWED_ORIGINS`에 승인된 member/ops origin 반영
   - 전환 중 old/new 동시 허용이 필요하면 명시적으로 기록
7. **Edge Function 배포**
   - 9-function repository contract 기준
   - 특히 `member-task-detail`, `admin-work-asset`가 ACTIVE + `verify_jwt=true`인지 확인
   - `push-dispatch`만 기존 의도대로 `verify_jwt=false`
8. **Edge auth smoke**
   - 보호 함수 unauthenticated request가 401/403
   - 실제 PII/지급정보 값을 로그에 출력하지 않는다.
9. **Static/runtime domain 변경**
   - `docs/v0.2.0-domain-cutover.md` inventory에 따라 canonical/runtime/robots/sitemap/routing 일괄 변경
   - `pnpm release:domain` PASS 또는 동일 계약을 독립 실행환경에서 확인
10. **Cloudflare static deploy / smoke**
    - member shell
    - ops shell
    - runtime asset fingerprint
    - old-origin redirect/recovery 정책
11. **Dedicated live auth E2E**
    - member login/logout/cache cleanup
    - admin login/member-detail/PII boundary
    - production money/task mutation은 하지 않는다.
    - GitHub Actions에서 실행할 필요는 없지만 적합한 runtime에서 실제 실행 증거가 필요하다.
12. **Final release decision**
    - Draft 해제 / merge / tag / launch 선언은 별도 최종 지시에서만 수행

## 3. 현재 STOP 조건

현재는 아래가 남아 있어 Production 적용을 시작하지 않는다.

- Phase 1 migration 미적용
- member/ops final mapping 미확정
- Auth/CORS final mapping 미확정
- `member-task-detail`, `admin-work-asset` 미배포
- auth-specific Playwright/runtime E2E 미확인
- dedicated live member/admin E2E 미실행

GitHub Actions quota 복구는 위 조건을 대신하지 않으며, 반대로 Actions가 없어도 위 gate를 각각 검증할 수 있다. GitHub Actions 자체는 STOP 조건에 포함하지 않는다.
